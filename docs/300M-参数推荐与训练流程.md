# Orbit 300M 参数推荐与训练流程

> 本文记录 Orbit 当前推荐器的实际输出。预计时间和可用内存会随设备、后台进程、数据量和训练实现变化；开始训练前以 App 中的实时推荐为准。

## 模型基础信息

- 模型档位：300M
- 当前架构参数量：约 284,070,912
- 本机目标：总内存约 25.8GB 时，训练安全需求约 9.1GB
- 默认设备：`auto`，由 Orbit 选择本机可用加速器
- 默认精度：`fp32`
- 学习率：`0.0003`
- 权重衰减：`0.1`
- 梯度裁剪：`1.0`
- 调度器：`cosine`
- 随机种子：`42`
- batch size：`1`
- 梯度累计：`1`

## 四种优化目标

以下不是论文规定的固定训练配方。App 会把当前实际语料 token、序列长度、batch、
梯度累计和目标遍历次数换算成 steps；下面只给出四个工程目标如何改变参数，具体
数值以 App 当前设备的实时推荐为准。

| 目标 | 作用 | 序列长度倾向 | 有效 batch 倾向 | 数据量/步数原则 | 论文依据 |
| --- | --- | --- | --- | --- | --- |
| 省时间 | 缩短单次实验 | 较短 | 保持内存安全 | 只减少本轮实验预算，不减少完整预训练所需 token | 没有统一论文固定值 |
| 省内存 | 降低峰值内存 | 较短 | 小 batch + 梯度累计 | token 目标不因省内存而偷偷减少 | LoRA/QLoRA 的内存思路主要适用于微调 |
| 平衡 | 作为默认起点 | 中等 | 由内存和吞吐测量 | 按实际 token 覆盖计算 steps | Chinchilla 约 20 token/参数基线 |
| 效果优先 | 增加上下文和验证预算 | 较长 | 在可承受范围提高 | 可增加数据丰富度和验证轮次，不保证只靠重复步数变好 | Llama 3 约 37 token/参数是规模实例 |

预计时间必须由当前机器实测单步速度重新计算；第一次启动、MPS 编译、数据准备和
教师 API 生成时间另计。修改步数、样本数、序列长度、batch 或梯度累计后，App 必须
重新显示 ETA，不能继续使用旧估算。

## 每个参数的作用和推荐

### Steps

优化器更新次数。增加步数通常增加训练时间，也可能让小数据集过拟合。

- steps 是 optimizer update 次数，不是样本数，也不是论文直接给定的模型质量指标。
- 计算近似为：训练 token ÷（序列长度 × batch size × 梯度累计 × 数据遍历次数）。
- 只有几十步通常只能验证流程；是否足够必须看独立验证集和 loss 曲线。

### Batch size

一次同时处理的样本数量。增大它会明显增加激活内存和每步耗时。

- 本机 300M：推荐保持 `1`
- 内存充足时也不要盲目增大；可优先使用梯度累计。

### Sequence length

每个训练窗口的长度。越长越能学习连续文档和代码上下文，但激活内存和单步时间都会增加。

- 省内存/省时间：先从 256～512 试验
- 平衡：按语料长段落和本机内存选择 512 左右
- 效果优先：只有本机内存和数据确实支持时才提高到 1024 或更长

### Gradient accumulation

累计多个小 batch 后再更新权重，可以用较低内存模拟大 batch。

- 300M 当前推荐：`1`
- 如果后续实现需要更大的有效 batch，可以提高该值，但总时间会增加；它通常比直接提高 batch size 更省内存。

### Learning rate

控制每次权重更新幅度。过高会不稳定，过低会学习缓慢。

- 当前 300M 推荐：`0.0003`
- 不建议在没有 loss 曲线证据时随意提高。

### Warmup steps

训练开始阶段逐渐提高学习率，降低刚开始训练时的梯度不稳定。

- 一般按总 optimizer steps 的约 1%～3% 计算起点；它通常不显著增加单步时间，
  但占用总步数的一部分。最终以 loss 稳定性调整，不使用固定 130/160/200。

### Weight decay

正则化参数，帮助抑制权重过度增大，降低过拟合风险。

- 当前推荐：`0.1`
- 每步额外开销很小，通常不是内存瓶颈。

### Gradient clip

限制极端梯度，避免 loss 变成 NaN 或训练进程崩溃。

- 当前推荐：`1.0`
- 不建议关闭。

### Precision

影响显存/内存、速度和数值稳定性。

- 当前本机 MPS/300M 推荐：`fp32`
- FP16/BF16 只有在对应硬件和训练路径验证稳定后再使用。

### Checkpoint interval

每隔多少步保存一次可继续训练的 checkpoint。

- 由预计总步数和可接受的恢复间隔计算。间隔越小，恢复能力越强，但会增加磁盘写入
  和保存时间；不能把 checkpoint 间隔误当成训练步数。

### AI 样本数

样本数影响主题覆盖面、教师 API 费用和生成时间，不直接等同于训练步数。

- 300M 从零预训练参考约 60 亿 token；按当前教师平均约 6,750 token/样本换算，
  约 888,889 条独立样本。这个数字是完整参考预算，不是要求一次生成。
- AI 辅助每轮允许 1～10,000,000 个样本；超过一轮就分批追加、查看和去重，防止
  API 费用、磁盘和内存失控。多轮训练必须保留样本来源和验证集。
- 从零预训练只用几十个样本无法得到可靠的通用聊天机器人；若目标是聊天，优先使用
  已预训练兼容基础模型做微调，并按 LIMA 的 1,000 条精心筛选样本研究基线开始，
  再根据任务覆盖和验证集补样，而不是机械复制同一数据。

## 预训练和微调选择

### 预训练第 1 次

选择：

- 训练方式：预训练
- 训练次数：1
- 基础模型：从零开始

主要使用文献、教材、技术资料、代码和代码注释，最后加入少量结构化任务、对话和 Orbit 身份样本。

### 预训练第 2～N 次

选择：

- 训练方式：预训练
- 训练次数：例如 2
- 基础模型：上一轮 Orbit 模型

Orbit 会检查父模型的训练轮次；预训练第 2 次必须接第 1 次，第 3 次必须接第 2 次，不能跳轮次，也不能混用不同模型规模。

### 微调

选择：

- 训练方式：微调
- 基础模型：已有本地 Orbit 模型

微调适合专业文献、标注任务和高质量指令对话；各类数据按验证结果动态调整，不固定为某个百分比。外部模型不能直接当作 Orbit 从零预训练；只有经过兼容架构、词表和 checkpoint 验证后，才允许作为兼容基础模型使用。

## 内存安全规则

Orbit 在训练开始前检查：

1. 模型规模需要的训练内存。
2. 当前可用内存。
3. 系统安全保留内存，目前下限为 1GB。
4. 训练过程中持续监控内存。
5. 内存接近危险阈值时停止并保存 checkpoint，之后可以继续训练。

多模型并行训练只有在每个任务都通过内存检查、并且总内存仍保留安全余量时才允许；否则任务必须排队或提示用户释放内存。
